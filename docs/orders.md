# 订单（草稿）与单据变更：实现与接口契约

两条链路解决同一个问题的两端：**还没成交的事别先进账**（订单），**已经成交的事不能就地改账**（变更单）。
两者共用同一套底层能力：明细 diff、`sourceOrderId` 关联原单、一次 git 提交落库、`requestId` 幂等。

## 一、订单（预售 / 预订）

### 为什么单独一个集合，而不是给销售单加 `status`
库存由 `rebuildStock(purchases, sales, items)` 全量派生（`api/routes.js`），**没有状态过滤**；
应收/应付、看板、对账也一律读那两个集合。草稿若住在 `sales.json` 里，哪怕一分钱没收也照样扣库存、进应收——
那不叫草稿，那叫已经成交。所以订单住在独立文件 `orders.json`：**不进库存、不进资金、不进债权**，随便改、随便删。

### 状态机

```
草稿(DRAFT) --过账--> 已过账(POSTED) --撤销过账--> 草稿
              ↑生成 X/C 单据          ↓删除那张单
```

- **过账**：按 `genOrderId('X'|'C', …)` 开一张正式单据（19 位单号），订单标 `postedOrderId` / `postedAt`；
  同时跑 `derive()` + `rebuildStock()`，库存与应收从这一刻才动。
- **撤销过账**：有条件允许。`canUnpost(doc, list)` 三闸门——已有 `payments` 流水、已有 `settlements` 核销、
  已有下级单（`sourceOrderId` 指向它）——任一命中即拒绝，钱已经进台账了不能凭空退回草稿。
  三闸门都空时删掉那张单、订单退回草稿。
- **删草稿**：未过账且没收过订金的随便删。**收过订金就禁止删除**（订金凭证已开，删了订单凭证就成孤儿）；
  已过账的先撤销再删。
- **孤儿兜底**：「清空数据」这类整库操作会把过账生成的单据直接删掉，留下状态还是「已过账」的订单——
  撤销找不到单、删除又要求先撤销，会永久卡住。因此撤销过账时单据不存在 → 直接退回草稿；
  删除已过账订单时单据不存在 → 允许原地删。

### 订金：订单阶段就能收钱
订金不是「虚拟金额」，是真金白银，因此收订金当场开一张正常资金凭证（`SK-` / `FK-`，
`category: 'deposit'`，`items[].orderId` 指向订单号）。过账时订金原样搬成新单的第一条收款流水，
**凭证号带着走、不改写已开凭证**。订金合计用 `orderDepositSum()`，与 `depositSumOf()` 同源。

### 编号与结构
- 订单号前缀 **`D`**：`D` + 年月日时分秒 + 本日 4 位流水（`D202610290930000001`），与销售单同规则、不同前缀，一眼可辨「这不是账」。
- `no` 字段留给客户/供应商那边的业务单号；过账时若没填，把订单号写进去，保证双向可查。
- 生成的单据带 `fromOrderId` / `fromOrderType: 'order'` 回指订单。
- 订单金额与单据同口径：`orderAmount()` = 合计 × 折扣链 − 整单优惠（`grossOf`），
  合计一律由明细行现算，不读 `total` 字段——草稿在界面上改来改去，`total` 可能是上一次算完没同步的旧值。

### 接口
`GET /api/orders` → 订单数组（**文件不存在返回 `[]`**，首次保存订单由事务自动建文件）。
`POST /api/orders` → **操作接口，不是整表覆盖**，`action` 取 `save` / `deposit` / `post` / `unpost` / `delete` / `clearDrafts`：

```json
{ "action": "save",   "order": { "kind": "sale", "customer": "客户甲", "date": "2026-10-29",
                                 "no": "", "remark": "", "photos": [],
                                 "items": [{ "code": "P00001", "name": "管件", "qty": 4, "price": 10, "total": 40 }],
                                 "discount": 0, "discountRates": [], "id": "可选，改草稿时传" } }
{ "action": "deposit", "orderId": "D20261029…", "amount": 100, "date": "2026-10-29", "remark": "订金" }
{ "action": "post",    "orderId": "D20261029…" }
{ "action": "unpost",  "orderId": "D20261029…" }
{ "action": "delete",  "orderId": "D20261029…" }
{ "action": "clearDrafts" }
```

- `clearDrafts`：一次请求删掉**全部纯草稿**，返回 `{ removed, skipped }`（`skipped` = 保留下来的张数）。
  它不绕过单张删除的两条硬约束——**已过账的不删**（要先撤销过账，否则那条正式单据会变成孤儿）、
  **收过订金的不删**（订金凭证已开）。因此它是幂等的：再调一次 `removed` 为 0、不会产生空提交。
  设计动机：给「清空草稿」按钮用，几十张草稿各发一次请求就是几十次 git 提交，既慢又会刷屏提交历史。

服务端返回 `{ ok, code, orderId?, removedDocId? }`；`code` 按操作含义不同（存草稿/删 = 订单号，过账 = 新单据号，收订金 = 凭证号），前端只用它做提示，落库结果一律以重新拉取为准。
校验函数 `validateOrder(order, { items })` 前后端共用（同一份 `src/utils/orders.js`），杜绝「界面能提交、服务端拒」；
订单只允许正数明细——**数量必须 > 0，退货请走单据变更**。

### 前端入口
- 菜单「业务 → 订单」，草稿数在菜单项上以角标显示，看板顶部另有「待过账订单 N 张 · 订金合计 ¥X」卡片（故意不跟随日期筛选：待办属于当下，不是某个区间）。
- 列表操作列按状态给按钮：草稿可 编辑 / 收订金 / 过账 / 删除；已过账只可 撤销过账，并给一个跳到生成单据的链接。
- 错误口径：`409` → 「数据已被其他操作更新，请点刷新后重试」；`5xx` → 「请以刷新后的数据为准」（结果未知，不能谎称失败）。

## 二、单据变更（增减商品）

### 为什么不让编辑弹窗直接改原单
一张已收款的单，明细一改，**金额（应收）、库存（派生）、资金（已开的 `SK-`/`FK-`）三者同时错位**，
而资金台账是只增不改的——改小原单等于凭空抹掉一笔真实进账。所以变更走「原单不动 + 生成关联单」：

| 变化 | 生成的单据 | 编号 | 符号 |
|---|---|---|---|
| 商品减少 | 退货单 | `XT-`（销售）/ `CT-`（采购） | 负数明细，走正常退款链路 |
| 商品增加 | 补差单 | `XA-`（销售）/ `CA-`（采购） | 正数明细，走正常收款链路（挂账） |

两张单都用 `sourceOrderId` 指回原单，库存与应收由派生层自动跟上。退货部分复用 `applyRefundOperation`
的四档资金处理（退现金 / 冲抵同单位欠款 / 转预存款 / 先退货暂不退款），**不另造一套钱的处理**。

### 什么时候锁、什么时候能原地改
`moneyTouched(order, kind)`（`src/utils/amend.js`，前后端共用）判定：有 `payments` 流水、有 `settlements` 核销、
或旧字段 `received`/`paid ≠ 0`（针对「`payments:[]` 但钱还躺在旧字段」的历史脏数据）——命中即视为动过钱。
另一条锁定原因是**本单已有下级单**：退货行按 `sourceLine`（原单行索引）定位商品，明细一改索引就错位。

编辑弹窗（`OrderEditDialog`）在锁定态：
- 明细整表改为**纯文本**（不铺一屏灰输入框）、快速添加换成提示文案、整单折扣/优惠/结算状态禁用；
- 锁定条 `.lock-bar` 放在 `el-form` **外面**——Element Plus 的 `<el-form :disabled>` 会级联禁用所有子组件（含按钮），
  放在表单里的「变更明细」按钮会点不动；
- 「实收金额」仍可编辑（补收是合法操作，下限 `cashFloor` = 已记现金流水）。

四个调用点（销售列表、采购列表、销售详情、采购详情）都嵌套了 `OrderAmendDialog`，继承同一套锁定与变更入口。

### 变更弹窗（`OrderAmendDialog`）
两张表：**① 要减少的商品（退货）** 行来自 `returnableLines()`（已扣掉历史退货量），可填退货数量或点「本单全退」；
**② 要增加的商品（补差）** 加行，**已有编码的单价锁回原单价**（变更不允许改价，改价请另开新单）。

预览区与服务端同一套纯函数（`diffOrderLines` / `refundPreview`）现算，因此界面显示的差额＝库里生成的差额：
原单应收/应付、本次退货 −、本次补差 +、变更后净成交金额。
**变更原因必填、无改动时提交按钮禁用**；提交前二次确认；请求体只传行索引与数量/编码，金额一律服务端重算。

### 幂等与「结果未知」
与退款一致：`crypto.randomUUID()` 生成 `requestId`，提交前存 `sessionStorage('stock.amend.pending')`；
4xx 明确失败 → 清掉标记、允许改后重试；5xx/网络断 → 结果未知 → 表单锁定并提示「上次提交结果待确认」，
重开同一张原单时会把 pending 填回来，按钮变「重试提交」（同 `requestId`，服务端命中 `dup` 直接返回，不会重复生成单据）。

### 接口
`POST /api/amends` → **操作接口**：

```json
{ "kind": "sale", "requestId": "<uuid>", "sourceOrderId": "X20261029…",
  "party": "客户甲", "date": "2026-10-29", "reason": "客户少要两件", "remark": "",
  "mode": "cash", "refundLines": [{ "index": 0, "qty": 2 }],
  "amendLines": [{ "code": "P00003", "name": "弯头", "unit": "个", "qty": 3, "price": 6 }] }
```

- `mode` 仅在 `refundLines` 非空时生效（纯补差不涉及退钱）：`cash` / `offset` / `deposit` / `pending`。
- 服务端逐条校验：`requestId` 必填且幂等、原单必须是正常单（退货单/补差单不能当变更源）、
  `party` 必须与原单一致（防止基于过期数据变更）、补差商品必须在商品库里、
  已有编码一律取原单行单价（前端价格不作数）。
- 返回 `{ ok, code, returnId, amendId, codes }`；`code` 取代表性单号（有补差取补差单，否则退货单）。

### 详情页展示
销售/采购详情页新增「关联变更单」卡片：列出原单 + 全部下级单，头部给「变更后净成交 ¥X · 未收/未付 ¥Y」
（`familyDocs` 口径：原单自身 + `sourceOrderId` 指向它的单，金额取 `grossOf` / `netOf`）。
列表页补差单在单号前显示「补」标记，与退货单一样不能当普通单编辑或再变更。

## 三、已知边界（有意不做）
- 变更**不允许改价**（改价请另开新单或先退货再重开），同商品在原单里有多个单价时直接拒绝变更。
- 补差单不参与原单的折扣链与整单优惠（按原价计），因此「净成交」只反映数量增减。
- 订金不可退：要退订金请先撤销过账（若无流水）或在单据里走退款，本期不做「订单级订金退回」。
- 过账后的价格修正只能靠「先退货、再开新单」，变更链路不承担调价职责。
