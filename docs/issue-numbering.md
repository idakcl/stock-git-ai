# 问题编号口径（Mxx / Bx）

## 结论先说

仓库里的提交信息用两套编号，**互不通用**：

| 时期 | 编号来源 | 范围 |
|---|---|---|
| 2026-10-31 之前 | 首轮《系统测评报告》原始编号 | 27 项，按问题类别排 |
| 2026-10-31 之后 | 《评测合并与整改报告》去重后的台账 | `M01`–`M63`（62 项合一 + 复核新增 M63） |

合并时按「同一问题只留一条」重排，**同一个编号在两套体系里指的不是同一件事**。
按合并表去查早期提交会找错条目，所以遇到不一致时，以提交正文描述的内容为准，编号只是索引。

## 已知对不上的提交

| 提交里的编号 | 实际修的内容 | 合并表编号 |
|---|---|---|
| `fix(M47)` | `--border-color` 自引用导致 23 处边框丢色 | M23 |
| `fix(M49)` | CSV 导出公式注入（`= + - @` 开头加单引号） | M24 |
| `fix(M34)` | AI 写预存/预付款流水补余额闸门 | M06 |
| `chore(M58,B6)` | 独立测试 workflow（非门禁） | 合并表 M58 是「负库存」，二者无关；该提交对应 B6 的配套 |

`fix(B7,B8)`、`fix(B3)`、`ci(B6)` 用的是 B 组编号，合并报告沿用了这组编号，可以直接对应。

## 之后的约定

1. 提交信息里的 `Mxx` 一律取**合并报告台账**的编号，不再使用首轮报告编号；
2. 编号后面必须跟一句主题（`fix(M05): AI 收款不再丢旧实付`），不写「按编号自查」这种只能靠猜的描述；
3. 一个提交修多条时，编号与主题按条目分别写清（`fix(M05,M09): …`）；
4. 若某个编号在合并表里找不到对应项，宁可不写编号，也不要拿旧号凑。
